# 多模型分级编排工作流

## 1. 先判断是否需要子代理

主代理先理解目标，再判断委派是否比直接完成更有价值。短问答、小改动、紧密耦合、需要连续对话或验证成本高于实现成本的工作，应由主代理直接完成。

只有满足以下至少一项实际收益时才委派：

- 子任务边界独立，能够真正并行。
- 大量检索或中间日志会占用主代理上下文。
- 需要不同于主代理的模态、上下文或成本能力。
- 子任务有足够工作量，且结果容易由主代理检查。

不要为了遵循固定流程而分别启动规划、实现和验证代理。主代理始终保留整体方向、集成和最终验收；子代理自报完成不等于验收通过。

## 2. 原生 Agent 与模型独立选择

普通任务优先使用原生 `explore`、`plan`、`coder`，保留 Kimi Code 原生提示词、工具和执行体系。原生任务不需要本插件的元数据。需要降低成本时，主代理可在 `Agent` 调用中显式选择模型池中的低成本别名；未显式选择时使用池内的高能力默认模型。

低成本模型只承担边界清晰、低风险、容易验证的文本任务。复杂架构、安全、并发、疑难调试和最终验收不能为了省钱而降档。失败或交付不足时由主代理修正、亲自处理或升级，不进行无上限的廉价重试。

按业务不变量而不是按技术层机械拆分。共享 RBAC、数据域、并发控制和跨模块接口应尽量只有一个所有者；`single`、`modality` 或 cost 策略不豁免安全判断。涉及权限、共享状态或高风险集成的工作，应由主代理或高能力模型负责，不能因统一使用 L1 而自动降档。

只有用户明确要求完整编排或调用严格编排命令时，才使用以下自定义固定权限 Agent：

| Agent | 权限档 | 用途 | 固定边界 |
| --- | --- | --- | --- |
| `mm-scout` | `read` | 代码检索、事实调查、资料收集 | 只读，无 Shell、无写入 |
| `mm-designer` | `read` | 模块内设计、接口与实施方案 | 只读，无 Shell、无写入 |
| `mm-implementer` | `write` | 指定文件、函数、模块或文档的实现 | 文件读写和 Shell |
| `mm-verifier` | `verify` | 运行测试、检查差异、收集验收证据 | 无直接编辑，可使用 Shell 检查 |

主代理选择自定义 Agent 类型即选定其固定权限档。子代理不能继续派生代理、联系用户、改变整体计划或宣布最终验收。默认不向这些 Agent 开放 MCP 工具；主代理应自行调用所需外部工具并把必要结果放入任务提示。

## 3. 选择等级模式和模态

分派前读取 `$KIMI_CODE_HOME/multimodel-orchestrator.routing.json`（未设置该环境变量时为 `~/.kimi-code/multimodel-orchestrator.routing.json`）；不存在时使用插件默认路由。根据当前 `version` 和 `mode` 选择任务等级，不要假定固定三级。

- **two-tier（默认）**：L1 表示边界清晰、低风险、容易验证的简单工作；L2 覆盖常规到复杂工作，包括跨文件功能、模块设计、疑难调试和复杂推理。特别高风险或目标不清的工作可由主代理直接完成。
- **single**：不再区分难度，所有受管子任务使用 L1 作为统一档位，但仍分别选择 text/image/video 模型。
- **modality**：不做难度分类，元数据中的 `tier` 使用 `any`，只根据 text/image/video 选择模型。
- **auto（自动分配）**：只使用 L1（简单、明确、低风险）和 L2（常规到复杂、需要较高工程判断）。主代理先判断任务，再调用本地候选程序。
- **旧配置迁移**：读取 version 1 或含 L3 的旧路由时，只在内存中把 L3 映射为 L2，并把 `worker-l3`、`worker-vision-deep` 分别迁移为 `worker-l2`、`worker-vision`。新分派不接受 L3，用户文件不会被改写。

无论哪种模式，都先判断委派是否有收益，不为小任务强行分级。同一个模型别名可以复用于多个等级和多个模态，不要求每个路由不同。

模态取完成该子任务实际需要的最高输入能力：

- `text`：只需文本和代码。
- `image`：必须理解截图、图片、图表或 UI 视觉证据。
- `video`：必须理解视频或时序视觉证据。

模态不能靠文件名猜测。如果主代理只会读取代码而不会向子代理提供媒体，则使用 `text`。需要图像或视频时必须选择声明相应能力的模型。

auto 模式的缺资料回退：

| 等级 | text | image | video |
| --- | --- | --- | --- |
| L1 | `worker-l1` | `worker-vision` | `worker-vision` |
| L2 | `worker-l2` | `worker-vision` | `worker-vision` |

模型的实际供应商、上下文长度和思维档位由 `[models]` 配置决定。不要修改插件受管副本来完成路由定制。需要为同一底层模型选择不同思维档位时，可注册不同模型别名；Agent 调用没有独立的 effort 参数。子代理默认统一使用 `[secondary_model] default_effort = "max"`，它只覆盖新派生子代理的模型默认档位，不改变主代理；不支持 max 的别名不得使用，不能静默降档。

## 4. 自动或手动选择模型

当前模式为 single、two-tier 或 modality 时，主代理按路由表直接选择模型，并设置 `selection: "auto"`。

当前模式为 auto 时，主代理先根据任务确定 L1/L2、模态和策略（balanced/cost/quality），再在 Bash 中运行本地候选程序：

```bash
python "${KIMI_CODE_HOME:-$HOME/.kimi-code}/plugins/managed/kimi-multimodel-orchestrator/scripts/auto_route.py" --tier L2 --modality text --strategy balanced
```

将参数替换为当前任务的实际值。读取输出中的候选模型、适配分、置信度和依据，由主代理选择第一个合适候选并向用户简要说明；不要把适配分当成统一 benchmark。`fallback: true` 表示资料不足，应使用返回的回退别名，不能自行编造分数或重新联网搜索。

联网资料来自用户显式执行 `/kimi-multimodel-orchestrator:evaluate-models` 后的 `model-insights.json`。没有执行该命令时不影响回退使用。verified=false 的模态不能使用，verified=true 只能补充能力，不能越过其他约束。

用户也可以明确指定模型池中的别名，例如“用 worker-l2 做这个 L1 任务”。此时设置 `selection: "manual"`，并在元数据和 `model` 参数中同时填写该别名。Hook 会检查该别名是否在路由配置中以及是否声明支持所需模态。未配置、未加入模型池或不支持所需模态的模型不能使用；主代理应说明限制，而不是静默换模型。

## 5. 建立唯一可执行契约

受管并行实现先由主代理在项目根目录建立 `orchestration.contract.json`，再分派实现。契约是子代理读取的唯一完整规范，主代理不得把完整接口、DDL 或安全规则重新复制到多份 Brief 中。可参考插件 `examples/orchestration.contract.json`。

契约至少包含：

- `canonical.types` 与可选 `canonical.schema`：实际类型和数据库定义的位置，不再在 manifest 中复制定义。
- `modules`：每个模块的 `path`、`owner`、`exports`、`tests`。`exports` 使用“导出符号 → canonical.types 中函数类型名称”的映射，使项目能额外通过类型检查绑定实现。
- `routes`：需要真实 HTTP 暴露的 `method`、`path`、`export`、`httpFile`，并将 `httpTest` 固定为 `required`。仅有 Service 函数不算完成路由集成。
- 需要权限控制时的 `security`：按 `authenticate → authorize_scope → optimistic_lock → state_transition` 排列检查顺序；用 `forbiddenErrorFields` 列出不得泄露的字段，用 `reportScope` 明确角色和数据域。

主代理拥有契约文件。子代理不得擅自修改契约；确需变更时，由主代理更新 `contractVersion`、重新通知所有者并重跑门禁。契约改变不得用于绕过原有红线或放宽验收。

子代理 Brief 只写契约路径与版本、模块目标、精确写入路径、指定单测路径和模块特有风险。禁止在 Brief 中重复抄写完整接口定义。子代理交付应简洁列明变更文件、实际检查结果、未执行项和风险，不粘贴整份源码。

## 6. 构造受管分派

每个新的受管 `Agent` 调用都要满足：

- `subagent_type` 是上表中的 Agent。
- `model` 是路由后的模型池别名，不能省略。
- `prompt` 以唯一的元数据注释开始，然后给出完整任务。

元数据格式：

```text
<!-- KIMI_MULTIMODEL_TASK
{
  "task_id": "T1",
  "summary": "实现用户设置接口",
  "tier": "L2",
  "modality": "text",
  "profile": "mm-implementer",
  "permission": "write",
  "selection": "auto",
  "model": "worker-l2"
}
-->
```

`task_id` 使用字母、数字、点、下划线或连字符。`summary` 是供工程悬浮窗展示的简短任务标题，应少于 80 个字符，不包含密钥、代码段或完整提示词。`profile` 必须与 `subagent_type` 一致，`permission` 必须与该 Agent 的权限档一致。元数据中的 `model` 必须与工具参数一致。

元数据之后，任务提示至少写清：

1. 目标、当前背景及契约路径与版本；不要假设子代理能看到主对话，也不要复制完整契约。
2. 输入材料、相关文件及已知接口；类型和跨模块签名以契约指向的 canonical 文件为准。
3. 工作范围、主代理分配的精确写入路径和明确不做的事项。
4. 需要使用的已授权工具；没有授权的工具不要要求使用。
5. 交付物、允许运行的指定单测文件路径、其他验证要求和统一 Handoff 格式。
6. 需要媒体分析时，给出可访问的媒体引用或路径。

**并行红线（适用于原生和 `mm-*` 子代理）：** 主代理必须把以下约束明确写入每个并行子代理的任务提示，不能用项目根目录代替具体分配范围。

- 严禁删除、重置、恢复、清理、移动或覆盖任何非分配路径的文件，无论使用文件工具还是 Shell；不得以测试隔离、修复失败或清理现场为理由越界。发现主代理或其他子代理的文件影响任务时，停止相关操作并交主代理处理。
- 测试检查只能针对主代理明确指定的单测文件路径运行，测试命令必须显式包含这些路径；禁止全库、目录级或无路径过滤的测试。未指定单测文件路径时不得运行测试，应在交付中注明未执行并交主代理验证。

独立的同类别、同等级、同模态、同模型任务可以并行。`AgentSwarm` 的 `prompt_template` 也要包含一个合法元数据块，`summary` 中应包含 `{{item}}` 或对应的简短项目说明，使悬浮窗能区分每个子任务；一次 Swarm 中的所有新任务共享所选权限档和模型。不同路由的任务应分批调用。并行实现任务应分配互不重叠的文件范围，并为每个子任务分别写明分配路径和指定单测文件路径，主代理负责集成、冲突检查和最终验收。

续跑已有子代理时使用 `resume`，不要重新指定模型；原生行为会保留其原模型。只有同一子任务的修正或补充才续跑，改变等级、模态或权限档时应创建新子代理。续跑提示同样不得放宽上述文件与测试红线。

## 7. 全部交付后的组合门禁

所有并行子代理交付后形成 join 点，由主代理显式执行门禁；不要在每个 `SubagentStop` 时对其他仍在写入的模块提前验收。

1. 先核对实际变更路径与分配范围，再运行契约结构检查：

   ```bash
   node "${KIMI_CODE_HOME:-$HOME/.kimi-code}/plugins/managed/kimi-multimodel-orchestrator/scripts/verify-contract.mjs" --root "$PWD" --contract orchestration.contract.json
   ```

   该脚本只检查契约、导出、类型引用、测试路径和 HTTP 绑定是否存在，不识别实际写入者，也不证明业务正确性。
2. 使用项目现有工具做类型和构建检查。TypeScript 项目存在 `tsconfig.json` 时运行 `npx tsc --noEmit`；其他项目使用其已有编译、类型或静态检查，不额外安装依赖。
3. 对契约中每个 `httpTest=required` 的路由执行真实 HTTP 调用。禁止用直接调用 Service 函数替代 HTTP 验收，必须覆盖路由绑定、身份头、状态码和响应字段。
4. 执行负向权限与数据库探针：无权限携带错误版本号仍应先返回 403，且响应不得包含 `actualVersion`；同区域不同 creator 的订单不得进入当前销售的数据域；数据库必须拒绝错误类型及状态互斥字段。

失败时只续跑原所有者并给出具体失败证据，修复后由主代理重新执行完整门禁。不要把 `tsc` 通过或子代理自报完成当作业务与安全验收通过。

## 8. 子代理交付与主代理验收

子代理最终消息必须包含：

- 任务 ID、状态、权限档和模型别名。
- 交付物及实现/设计/调查细节。
- 新建或修改文件的位置；没有文件变更时明确写“无”。
- 实际执行的检查及结果，未执行的检查单独列出。
- 风险、未解决问题和需要主代理处理的事项。

主代理收到后必须检查完整性并核对真实文件和验证证据，优先使用定向 diff、契约门禁和测试证据，不逐行长篇复述全部源码。`mm-verifier` 只能提供额外证据，不能替代主代理验收。主代理应亲自处理集成、必要的复测和最终用户交付。

失败、受阻、测试不通过或上下文不足时，主代理重新评估任务。需要更强能力时，由主代理提高等级或改选模型并发起新分派；子代理不得自行升级、扩大权限或绕过主代理。
